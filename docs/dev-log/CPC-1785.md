# CPC-1785 Development Log

Date: 2026-09-23

## Objectives

- Convert only the legacy AngularJS Add Product page into a modal.
- Open the Add Product form from the Product List.
- Preserve the existing `/product/new` route and product creation behavior.

## Technical decisions and reasons

- Reused the existing Angular UI Bootstrap `$uibModal` dependency already loaded by the legacy application.
- Opened the existing `product-form` component from the Product List instead of creating a second Add Product form.
- Kept the `/product/new` route unchanged so existing direct links continue to resolve.
- Added modal-aware behavior to the existing form controller: component-modal bindings dismiss or close the modal, while direct-route instances continue to navigate to `productList`.
- Used the existing Bootstrap styling conventions and a scoped modal class for centering and viewport scrolling.

## Problems encountered and solutions

- The existing form controller assumed it was always running under a UI-Router state and called `$state.go('productList')` after creation. The initial injector-based `$uibModalInstance` detection did not work for a nested component, so the modal was changed to Angular UI Bootstrap component mode with explicit `close` and `dismiss` bindings.
- The existing Add Product button navigated to the route. It now opens the modal while leaving the route registered.
- After rebuilding the API Gateway, the Add Product backdrop appeared but the modal content was not visible. The global `.modal` selector in `css/vets/modal.css` was overriding the Angular UI Bootstrap modal window's display, dimensions, position, transform, background, and stacking styles.
- After the first scoped override, the backdrop still appeared while the dialog remained invisible. DevTools showed a negative dialog position; Bootstrap 5's fade rules were applying opacity/visibility and a negative dialog transform because Angular UI Bootstrap 2.5.6 uses the older `in` modal state convention rather than Bootstrap 5's `show` convention.

## Close button follow-up

- Problem: The Add Product modal opened correctly, but its X close button was not visible.
- Root cause: The template uses the legacy Bootstrap `.close` class, while the application loads Bootstrap 5 CSS and does not provide the older close-button presentation reliably.
- Solution: Added styles scoped to `.product-add-modal .modal-header .close`, positioning the button in the upper-right corner with explicit visibility, color, size, and stacking. The existing `$ctrl.close()` handler, form, scrollbar, backdrop, and outside-click behavior were preserved.
- Verification at that stage: The template and selector wiring were inspected. Later Chrome verification confirmed the X button behavior documented above.

## Component modal integration follow-up

- Problem: Chrome showed only the Submit button because the X button was inside `ng-if="$ctrl.isModal"`, while the component controller could not obtain `$uibModalInstance` through `$injector` when loaded from a string-template modal.
- Solution: Changed the Product List modal to use Angular UI Bootstrap's `component: 'productForm'` API. The component now receives UI Bootstrap's `close` and `dismiss` bindings, and the controller uses those bindings to identify modal mode, dismiss from the X button, and close with the created product after a successful API call.
- Route compatibility: The existing `/product/new` state still uses `<product-form></product-form>` without modal bindings, so it continues using direct-route navigation behavior.
- Files changed: `product-list.controller.js`, `product-form.component.js`, and `product-form.controller.js`. Existing modal CSS and the product form template were not changed in this step.

## Product Details product ID fix

- Problem: The Product Details modal opened, but Chrome showed `GET /api/gateway/products/undefined` with status 422, so the product and image were not displayed.
- Root cause: Angular UI Bootstrap component modals expose resolved values through the component's `resolve: '<'` binding. The component had incorrectly declared `productId: '<'`, so the `resolve.productId` value was never available as `$ctrl.productId`.
- Solution: Replaced the incorrect direct `productId` binding with the standard `resolve` binding and updated the controller to read `self.resolve.productId` before falling back to `$stateParams.productId` for the direct route.
- Verification: JavaScript syntax checks and `git diff --check` passed. Manual Chrome verification confirmed the resolved product ID loads the selected product and its uploaded image successfully.
